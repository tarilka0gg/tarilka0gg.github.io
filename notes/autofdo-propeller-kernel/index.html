Building the kernel with AutoFDO and Propeller

Profile-guided kernel layout on a laptop: what to record, which tool reads it, and why clang 22 breaks the chain.

  • Sep 2026
  • Clang, AutoFDO, Propeller, perf
  • Source

The goal

I build my own kernel for the Victus (7.1.8 with the CachyOS patches, BORE scheduler, Clang). After the plain Clang build, the next step with the most expected gain for a gaming laptop is profile-guided layout: AutoFDO tells the compiler which branches are hot, and Propeller then reorders functions and basic blocks in the final link to keep hot code together. The chain has a version trap that is easy to miss. This note is the chain as I ran it in September 2026.

The chain

  1. AutoFDO profile. Record the kernel running a realistic workload, convert it to a .afdo file.
  2. P1 build. Build a kernel with the AutoFDO profile applied and Propeller-capable (CONFIG_AUTOFDO_CLANG=y, CONFIG_PROPELLER_CLANG=y). Keep its unstripped vmlinux, and boot it.
  3. Propeller profile. Record the booted P1 kernel with a different perf event and convert with create_llvm_prof.
  4. Final build. Rebuild with both profiles and link with ld.lld.

Step 1: the AutoFDO profile

I recorded the whole system with a branch stack while the kernel compiled:

perf record -b -e cycles:kp -a -N -c 500009 \
      -o kernel-compilation.data

I stopped it with SIGINT when the workload ended. It took three attempts. The first (19 GB) had no -b, so no branch stack, and was unusable. The second (26 GB) used the same command as the third; I did not record why I switched. The third, 62,270.6 MiB, was the one I used. I converted it with llvm-profgen from LLVM 22:

llvm-profgen --kernel --perfdata=kernel-compilation.data \
      --binary=/usr/src/linux/vmlinux -o kernel-compilation.afdo

The conversion took about 3.4 hours, needed a TMPDIR outside / because the temporary files are large, and produced a 2,921,700-byte profile. The kernel takes it through CLANG_AUTOFDO_PROFILE. That is the variable name; AUTOFDO_PROFILE_foo.o := y in the kernel docs is a different, per-object switch.

Keep the right vmlinux. My 62 GB recording had no BUILD_ID section in its header (likely because the recording ended with a signal), and by the time I wrote this down the vmlinux it was recorded on had been overwritten by the next build. The timeline shows the profile came from build #3 while the only vmlinux on disk was #4, so I can no longer re-derive the profile from the raw data. To redo it: boot the kernel you want a profile for, save its vmlinux, check readelf -n vmlinux | grep 'Build ID', record, and convert against that same file.

Step 2: the P1 build, and the trap

The P1 build is a normal Clang build with the AutoFDO profile. I ran it with clang 19, and this is the important part.

make CC=clang LLVM=1 LLVM_IAS=1 LD=ld.bfd HOSTLD=ld.bfd \
     CLANG_AUTOFDO_PROFILE=/path/to/kernel-compilation.afdo bzImage

Propeller needs the compiler to emit a basic-block address map (SHT_LLVM_BB_ADDR_MAP) into vmlinux, and the profile converter reads it. The converter is create_llvm_prof from google/autofdo, and it only understands map versions up to 2. Clang 19 writes version 2. Clang 22 writes version 5, and the tool refuses it:

unsupported SHT_LLVM_BB_ADDR_MAP version: 5

My system compiler is clang 22 and my AutoFDO kernel was built with it, so that kernel's vmlinux could not be used for Propeller. The fix is to build the P1 and final kernels with clang 19, by putting it first on the PATH (PATH=/usr/lib/llvm/19/bin:/usr/lib/llvm/22/bin:$PATH). I did not wait for a newer converter. Whoever tries this with a newer toolchain should check the map version first.

I built create_llvm_prof myself from the git repository, with its vendored LLVM. It would not build as is: the first four attempts failed (the third, for example, on errors in the bundled abseil headers). I patched it to build against the system abseil instead of the vendored copy, and the fifth build linked.

I keep vmlinux-p1 (the unstripped file, about 249 MB) and boot the P1 kernel. This matters because the next step checks the build-id of the binary against the profile.

Step 3: the Propeller profile

The Propeller profile has to be recorded on the booted P1 kernel only. create_llvm_prof compares the build-id in vmlinux-p1 with the one in the recording and refuses anything else. The event is also different from AutoFDO: Propeller wants taken branches, not cycles.

perf record -e BR_INST_RETIRED.NEAR_TAKEN:k -a -N -b -c 500009 \
      -o propeller.data -- sleep 1800

Thirty minutes of system-wide recording produced a 820.7 MB file (about 40 MB per minute). Converting it was fast:

create_llvm_prof --binary=vmlinux-p1 --profile=propeller.data \
      --format=propeller --propeller_output_module_name \
      --out=propeller_cc_profile.txt \
      --propeller_symorder=propeller_ld_profile.txt

The conversion took 23 seconds. It writes two text files: a compiler profile (cc_profile), which lists hot functions and basic-block ids per source file, and a linker profile (ld_profile), which is a symbol order. They are 354 KB and 175 KB. The raw recording is not worth keeping once they exist.

Step 4: the final build and the linker

The final build is the same command with two additions: the Propeller profile prefix and a different linker.

make CC=clang LLVM=1 LLVM_IAS=1 LD=ld.lld HOSTLD=ld.bfd \
     CLANG_AUTOFDO_PROFILE=/path/to/kernel-compilation.afdo \
     CLANG_PROPELLER_PROFILE_PREFIX=/path/to/propeller bzImage

I link with ld.lld: the linker profile is applied through --symbol-ordering-file, which only lld supports, so ld.bfd, which I use for the P1 build, cannot be the final linker. There is no lld 19 on my system, so the final link used lld from LLVM 22 even though the objects were compiled with clang 19. That worked.

I reused the modules from the earlier AutoFDO kernel build (same configuration, MODVERSIONS disabled, same version string), which let the proprietary NVIDIA module load without a rebuild.

Since then I have rebuilt the kernel a few more times for config changes (kexec, touchpad and KVM options, going by my build log names).

Results

The honest answer is that I have no clean number. The only evidence I have is that I noticed steadier FPS in games on the Propeller kernel than before. That is a subjective report, not a measurement: I did not run a controlled A/B. I ran benchmarks on the Propeller kernel (7-Zip, Blender and y-cruncher results are in my work folder), but with no like-for-like baseline I will not quote them as a gain.

Measurable facts I do have: the AutoFDO profile was about 2.8 MB from a 62 GB recording, the Propeller recording was 0.8 GB from half an hour of load, and its conversion takes seconds. After the P1 boot, the Propeller cycle is about 30 minutes of recording plus one rebuild.

What I would do differently, and open questions

  • Save the vmlinux of every kernel I record on, along with its build-id, before building the next one.
  • Record AutoFDO on a kernel that I also keep; mine cannot be reproduced.
  • Pin the toolchain versions in the build script. The clang 19 requirement lives only in my notes and in the PATH I type.
  • Measure properly. A fair comparison needs the same config, the same workload, the plain Clang build, the AutoFDO build and the Propeller build, repeated several times.
  • I do not know whether a newer create_llvm_prof reads map version 5. Until then, the compiler and the converter have to stay on versions that agree.
