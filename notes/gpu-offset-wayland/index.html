Applying an NVIDIA GPU clock offset on Wayland

NV-CONTROL needs an X server. On a Wayland-only machine, I start one for a second at boot and shut it down.

  • Sep–Oct 2026
  • NVIDIA, Coolbits, Wayland, OpenRC
  • Source

Clock offsets change the voltage/frequency curve of the GPU. The values here (core +125 MHz, memory +250 MHz) are for my RTX 4070 Laptop GPU and my silicon only. Another chip may be unstable at them. Running the script repeatedly by hand under heavy GPU load once caused a real GPU fault on my machine (details below). Start with small offsets and test on your own hardware.

The problem

I run a Wayland-only desktop (niri) on Gentoo with OpenRC. The laptop has an NVIDIA RTX 4070 Laptop GPU, and I wanted a tuned clock offset applied at every boot: core +125 MHz and memory +250 MHz, with no clock lock. The GPU still boosts freely. It runs on a raised voltage/frequency curve, so it reaches the same clocks at lower voltage. I also wanted GPUPowerMizerMode=1 (prefer maximum performance) set in the same pass.

With the proprietary driver on Linux, the offsets can only be reached one way.

Why it is awkward

The attributes are GPUGraphicsClockOffsetAllPerformanceLevels and GPUMemoryTransferRateOffsetAllPerformanceLevels. They are exposed only through nvidia-settings, which talks NV-CONTROL to a real X server that has the NVIDIA driver loaded, and only if the X server was started with Coolbits enabled. The alternatives do not work:

  • NVML, the library behind nvidia-smi, has no public API for these offsets.
  • XWayland does not load the real NVIDIA driver, so it cannot expose NV-CONTROL either.
  • On a machine without any X server there is nothing for nvidia-settings to talk to.

So the script starts its own X server, applies the offsets, and shuts it down again.

The method

The solution has three small pieces. The first is an Xorg config that turns Coolbits on. Without Coolbits the nvidia-settings attributes silently do not exist, so this file is what the whole thing depends on. It goes in /etc/X11/xorg.conf.d/20-nvidia.conf:

Section "Device"
    Identifier "NVIDIA Card"
    Driver "nvidia"
    Option "Coolbits" "28"
EndSection

This needs x11-base/xorg-server installed, even though the system is otherwise Wayland-only.

The second piece is the script, gpu-undervolt-apply. It must run as root and has the two offsets as variables at the top. Its core, with the checks trimmed:

CORE_OFFSET=125
MEM_OFFSET=250
VT="vt7"

nvidia-smi -pm 1 >/dev/null          # persistence mode
ORIG_VT="$(fgconsole 2>/dev/null || echo 1)"

coproc XORGCO { exec Xorg -displayfd 1 "$VT" -config "$XCONF" \
                -logfile "$XLOG" -ac 2>/dev/null; }
read -r -u "${XORGCO[0]}" DNUM        # Xorg writes its display number here
DISP=":${DNUM}"

DISPLAY="$DISP" nvidia-settings -a "[gpu:0]/GPUGraphicsClockOffsetAllPerformanceLevels=${CORE_OFFSET}"
DISPLAY="$DISP" nvidia-settings -a "[gpu:0]/GPUMemoryTransferRateOffsetAllPerformanceLevels=${MEM_OFFSET}"
DISPLAY="$DISP" nvidia-settings -a "[gpu:0]/GPUPowerMizerMode=1"

Three details make it dependable.

  • -displayfd. Xorg picks a free display number itself and reports readiness by writing the number to a pipe, so there is no sleep-and-poll loop and no fixed :1 that could already be taken.
  • A free VT. Xorg starts on its own virtual terminal (vt7).
  • A cleanup trap. On exit, including failure or interrupt, the script kills the server and switches back to the original VT.

The third piece is an OpenRC service, gpu-undervolt-apply.initd. It belongs in the boot runlevel (rc-update add gpu-undervolt-apply boot), and its dependencies say need modules, after modules and before display-manager. That ordering is the point: it runs before any getty or login starts the Wayland session, so the VT switch happens while nothing is on screen.

depend() {
	need modules
	after modules
	before display-manager
}

The service applies the offsets again at each boot. The repository also has a release tarball with install and uninstall scripts and the service files.

Known limitation: both monitors blink on a manual run

Starting the second Xorg does a real VT switch, which pauses the whole Wayland session, including outputs on the integrated GPU, not only the NVIDIA-attached one. About 1.5 seconds of it is Xorg doing a real modeset and DisplayPort link training on the connected external monitor, even though I only want NV-CONTROL. I tried Option "UseDisplayDevice" "none" together with AllowEmptyInitialConfiguration, and neither avoided it. My guess is that nvidia-drm.modeset=1 bypasses that older option. I accepted it: at boot nothing is on screen yet, so I only see it when I re-run the script by hand to test new values.

Care when re-running by hand

Running the script repeatedly in quick succession while a game was under heavy load caused a real Xid 109: CTX SWITCH TIMEOUT GPU fault, and once left an output stuck disabled (nvidia-modeset: Invalid request parameters) until I rebooted. Before testing new values, check that the GPU is not busy and that it has free memory:

nvidia-smi --query-gpu=memory.free

With little free VRAM the headless Xorg fails outright with "Failed to allocate primary buffer: out of memory". The script catches that case and prints a hint that points to /tmp/xorg-undervolt-apply.log.

How I tested it

I tested the script mostly by running it by hand while trying values, which is where the two problems above came from. I did not record a benchmark or a stability test for this offset, so I make no claim about the size of the gain. The reasoning is only the usual one for a raised curve: the same clocks at a lower voltage means less heat. The lab data for the rest of this machine's tuning is in the first note, and the power scripts are in power-scripts.

What I would do differently, and open questions

  • The VT switch is the ugly part. It is acceptable at boot and awkward for tuning. A route that does not need an X server would be better. I know of none through NVML.
  • Without a measurement I cannot say where the stability limit of my chip is. A proper search would need a test on the GPU, like the CPU one in the first note, with offsets stepped up until it fails.
  • The service runs the script from my home directory, and the offsets are constants in the script. Both are fine for one machine and wrong for a packaged tool.
