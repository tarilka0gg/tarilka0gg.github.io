BIOS unlock and CPU undervolt on the Victus 16

Patching the BIOS so the voltage mailbox works, finding the power caps behind 44 W, and what the undervolt actually gained.

  • Jul–Aug 2026
  • BIOS, undervolt, RAPL, EC, fans
  • Source

Every number on this page is for my own silicon: an i7-14650HX in an HP Victus 16 (board 8C99, BIOS F.15). Every die has its own margin, and on a different board the same BIOS offsets mean something else. Do not copy these values. A wrong undervolt can corrupt data without a crash, and a wrong BIOS write can leave the laptop unbootable.

The problem

Under full load the laptop sat at 44 W and about 2.1 GHz. I remembered it pulling 120 W, and a game I play (Rust) had frame drops. I wanted an undervolt, so the same power budget would buy more clock. That turned into three separate problems: the BIOS hid the voltage controls, a software cap I had forgotten about held the power down, and the embedded controller (EC) throttled on its own timer. I worked on it from 24 July to 1 August 2026, in 29 sessions that I logged in a journal.

Step 1: the OC mailbox was dead

Undervolting on Intel goes through the overclocking mailbox, MSR 0x150. On this laptop intel-undervolt and throttled both reported Values do not equal: the write was accepted and then read back as zero. The locks (CFG Lock, OC Lock) were already clear on the live CPU. The problem was the master switch, OverClocking Feature in the BIOS CpuSetup variable, which was 0 and made the mailbox ignore writes.

I could not set it from the OS. The Insyde H2O firmware rejects runtime SetVariable for Setup variables (EROFS); it only works from boot services, such as a UEFI Shell. I prepared a USB stick with setup_var.efi, and in the end I flashed a patched BIOS image instead, so a reset to defaults would not undo the change.

The patch, in outline:

  • I parsed the variable store of three images and listed every *Lock option in the setup forms.
  • I set OverClocking Feature to 1 and cleared CFG Lock, Overclocking Lock, a third lock, PROCHOT Lock, HwP Lock and Tcc Offset Lock.
  • I applied this to all 5 copies of CpuSetup inside the image (three defaults blocks, the working NVRAM copy and its backup). The image holds several copies, and a reset to defaults would restore the unpatched one.
  • Before flashing I checked the 14 changed bytes in every copy (verify-final.py).

On 26 July I flashed it. After the first boot I checked that a write holds, because reading zero is ambiguous (it can mean "dead" or "offset is really 0"). I stopped throttled, which writes zeros every second, applied -50/-30/-50/-30 mV and read the same values back. The mailbox was alive.

I publish no BIOS images and no variable dumps. My images contain the machine serial number and other identifiers, and the layout of the Setup variables depends on the BIOS version, so a dump restored onto another version breaks settings. The repository has only byte-level patch tables and a script that checks the old byte at every offset and refuses to run on a mismatch.

Step 2: the 44 W cap was software

The 44 W limit was not the EC and not the BIOS. Session 4 found two caps stacked. throttled was rewriting PL1/PL2 every few seconds in two places, the RAPL MSR 0x610 and the memory-mapped copy at MCHBAR+0x59A0. The MMIO copy takes priority, so raising only the MSR did nothing. Neither was locked, so the fix is plain config: /etc/throttled.conf, sections [AC] and [BATTERY].

[AC]
PL1_Tdp_W: 80
PL2_Tdp_W: 115
Update_Rate_s: 1

With 80/115 W the package drew 80.0 W under a synthetic load, at 81 to 82 degrees C.

Step 3: the EC's turbo budget

Even with both registers at 80 W I sometimes saw 45 to 54 W. I ruled out the clamp bit, cTDP, HWP/EPP and something overwriting the registers. The real cause is in the EC: until something writes to /sys/firmware/acpi/platform_profile, it keeps its own lower limit. After a write it grants full PL1 for only about 2 to 2.5 minutes, then drops to about 45 W (the HWP guaranteed level). The write is what matters, not the value; writing performance when the profile is already performance still rearms it, while powerprofilesctl does nothing in that case.

echo performance > /sys/firmware/acpi/platform_profile

A small OpenRC daemon, sustained-turbo, repeats that write every 90 seconds under load. It cost nothing at idle: after a compile finished, the same machine drew 14.8 W at 55 degrees C with the fans stopped. To see real draw I read the energy counter (0x611); the 0x610 register only shows the configured limit. The scripts are in power-scripts.

One more dead end: switching the configurable TDP level (MSR 0x64B). The level registers are read-only, and moving to Level2 (65 W) at the same measured power halved the P-core clock (4397 to 2196 MHz). The EC treats the change as a signal to cut the turbo ratio. I put it back to nominal and left it alone.

Step 4: the undervolt, and a methodology mistake

The voltage offsets go in the same throttled.conf, under [UNDERVOLT.AC] and [UNDERVOLT.BATTERY]. I did not use intel-undervolt apply at the same time: both write MSR 0x150, so they race.

The gain only shows when the load is power-bound. In my first runs I used a mixed load that never reached the power limit, and every undervolt looked like "nothing" (the clock barely moved). Those rows are flagged MIXED-INVALID in my data. With a power-bound all-core load at PL1 = 80 W:

Offset (CORE / CACHE)All-core clockCore voltagePackage drawTemp
0 / 02733 MHz950 mV80.0 W80 C
-100 / -100 mV3553 MHz908 mV80.0 W83 C

That is +30% clock at the same power. A second pair of runs at -120 mV agrees (P-cores 3435 to 3894 MHz, core voltage 961 to 917 mV). In the sweep at -100, -120 and -140 mV the clock rose in steps, from 3567 to 3583 to 3705 MHz, each at 79.9 W.

The mistake was trusting one all-core test. This CPU runs at two very different voltage/frequency points:

  • all-core: about 3.9 GHz at 0.89 V;
  • light-load boost with 1 to 4 threads active: 4.6 to 4.9 GHz at 1.03 to 1.13 V.

CORE -160 passed the all-core test and failed on boost. Every failing point showed zero WHEA and zero MCE events, so the kernel log tells you nothing. The only detector that worked was compute correctness, using y-cruncher in stress mode, once on all threads and once pinned to 1 or 2 threads:

/opt/y-cruncher/y-cruncher stress -M:4G -D:60 -TL:600

The same command, pinned to one or two threads with taskset, covers the boost point (my boost-test.sh does this).

I look for Exception, Mismatch and : Failed in the output. The config line Stop on Error: Enabled is harmless and easy to mistake for a failure.

Measured limits

"Passing" means the point survived y-cruncher on all-core and on light-load boost at PL1/PL2 = 80/115 W. It is not a guarantee of everyday stability.

DomainLast passingWhere it breaks
CORE-150 mV-160: silent failure on boost; -165: also on all-core
CACHE-175 mV-180: fails on light-load boost
GPU (iGPU)-150 mVno break point found
UNCORE / System Agentleft alone: memory controller, PCIe, display engine; the risk is silently corrupted memory
ANALOGIOleft alone: it gives nothing

The CACHE sweep ran at CORE -140 and CORE -150. Offsets of -150 to -175 mV passed both tests; -180 failed on boost. At CORE -160, CACHE -175 failed on boost, and at CORE -165 every CACHE value failed on all-core, so the CACHE limit only means something if CORE is at or above -150.

CORE drives the voltage of the shared core and ring rail. I checked this by asking which setting is holding the voltage: CORE -20 mV moved the measured rail by 17 mV, CACHE -20 mV by 2 mV, which is noise. CACHE does not move the voltage, but it has its own stability limit.

I settled on CORE -150, CACHE -175 and GPU -150 at 80/115 W as the last fully validated point. Later I changed the live values (see the open questions).

Fans

The laptop has two fans on the hp_wmi driver, which exposes a shared pwm1 (0 to 255) and pwm1_enable (2 is automatic, 1 is manual). Manual control works: a test write moved the fans from 3900/4200 to 4400/4400 RPM in 3 seconds, and the driver rounds values to steps (I wrote 220 and got 193).

The fans went quiet under load for a reason I found in the driver source. Every write to platform_profile puts the EC into a user-defined thermal state for 120 seconds. My rearm loop writes every 90 seconds, so the EC never returned to the automatic curve that pwm1_enable=2 depends on. On this board the driver has no fallback table, so the automatic curve did not work at all while the daemon was active. The daemon now drives the fans itself, from the package temperature, and hands control back to the EC when it stops. In the first version the curve was a minimum of pwm 90 (about 1900 RPM, never 0) below 70 C, 140 from 70 C, 193 from 80 C and 255 from 90 C. Later I extended it with a power-based curve as well.

A manual fan curve has no protection of its own: a low PWM under load means overheating with only the hardware thermal shutdown left. Tie any permanent curve to a real temperature sensor.

Result

With the EC rearmed, EPP set to performance, C3 disabled (it caused input micro-stutters on AC) and gamemode, Rust ran at 130 FPS for the first time. During that session the CPU drew 41 W and the GPU was at 94% utilisation, so the GPU had become the limit. That is a single observation from one game, not a benchmark. Disabling C3 costs idle power on battery: 44 W against about 26 W with it enabled.

Rollback

Stopping throttled does not clear the offset: what was written to MSR 0x150 stays until it is overwritten or the machine reboots. To roll back:

  1. Set every value in [UNDERVOLT.AC] and [UNDERVOLT.BATTERY] (CORE, GPU, CACHE, UNCORE, ANALOGIO) to 0 in /etc/throttled.conf.
  2. rc-service throttled restart. It writes zeros to the mailbox every second. If the system still misbehaves, reboot.
  3. Read the mailbox back with a read-only script. All five domains should show +0.0 mV. A non-zero value means the rollback has not happened.

throttled reapplies its config at boot, so an unstable value survives a reboot. If a machine will not stay up, run rc-service throttled stop right after boot and fix the file. The signs of silent instability are not crashes: corrupted archives, compile errors that do not reproduce, odd compute results. To undo the BIOS change itself, reflash the original image. I kept it, and I checked that my patch script reproduces the flashed image byte for byte from it. My scripts that write to MSR, sysfs or EFI refuse to run on a different board (exit code 64).

What I would do differently, and open questions

  • Test boost and all-core from the start. The mixed-load runs and the all-core-only tests both gave misleading answers.
  • The live config drifted from what I validated: on AC it runs 95/135 W (validated at 80/115), CACHE 0 and GPU -120. My y-cruncher check at 95/135 W never finished, so that combination has no verdict.
  • On battery the live CORE offset is -210 mV, while the journal records -150. Nothing documents the -210 and there are no y-cruncher logs behind it. Battery uses much lower power limits, so the voltage regime differs, but that is an assumption.
  • I never found why the auto mode of sustained-turbo kept dying silently, with nothing in dmesg or the cgroup counters. I switched it to an always-rearm mode that holds no state. The resume hook that rearms the EC after sleep has never been checked against a real suspend.
