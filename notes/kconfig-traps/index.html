Kconfig traps from building a kernel matrix

Fragments on a fixed seed, a verifier for options Kconfig silently drops, and the specific traps I found.

  • Aug–Sep 2026
  • Kconfig, kernel configs, Gentoo
  • Source

The problem

I needed a ready kernel image for every common hardware combination for my distribution, Simple Linux, without tuning each one by hand. kernel-matrix is my answer: a config is a merge of small Kconfig fragments on top of a shared seed, one fragment per CPU, GPU, platform, laptop embedded controller (EC) and modem. This note is about the part that took the most time: Kconfig quietly throws away things you ask for, so the matrix needed a checker, and I collected a list of the specific ways it bites.

The fragment values are tuned for my own builds (Gentoo, the CachyOS 7.1.x kernel). Treat them as a starting point. The only build-and-boot check I have done is on my own Victus. I have no other hardware, so the kernels for other machines are checked as configs and builds, not as boots.

How a config is assembled

For one combination the order is a fixed seed, then two shared fragments, then one fragment per dimension:

seed/default.config
  common/base.config, common/hardware.config
    cpu/intel-raptorlake.config
      gpu/nvidia.config
        platform/laptop.config
          ec/hp.config
            modem/none.config

The merge is the kernel's own scripts/kconfig/merge_config.sh -m, followed by conf --olddefconfig, which resolves dependencies. Later fragments override earlier ones, so order matters. For example cpu/intel-raptorlake disables X86_NATIVE_CPU, which the seed turns on. The scripts call conf directly with KCONFIG_CONFIG pointing at a target file, so generating a config never touches the .config of an already-built kernel tree and needs no make O=....

DimensionFragmentsWhat it does
cpu19instruction set level and micro-architecture, from Sandy Bridge to Arrow Lake, AMD btver2 to Zen 5, plus generic x86-64 v2 and v3
gpu7the DRM driver for the vendor; hybrid laptops also get the iGPU driver
platform5laptop, desktop, handheld, server, and one model-specific layer for my Victus
ec11vendor laptop drivers, almost all as modules
modem4WWAN and modem drivers

The full product with no filters is 23,408 combinations, and the repository holds 7,614 target files. In the end I dropped EC and modem as axes. Their fragments only set =m, and a bzImage build does not depend on modules, so dozens of EC and modem variants produced an identical vmlinux for every CPU, GPU and platform. Every target now simply enables ec/all and modem/all. That gives 678 compact targets, and a hand-weighted popularity score (weights I set by hand in a script, not market data) picks the top 304 to build.

Why a fixed seed

At first the seed was the .config of the machine doing the build. That was a mistake: anything my Victus does not have was silently off, and the state of the build tree leaked into every kernel. The seed is now a file in the repository, my 7.1.6 trim11 config with 2,816 =y and =m options. If the file is missing, the script warns and falls back to the tree's .config.

The two shared fragments exist for a similar reason. common/base.config (14 options) holds hardware-independent things, such as filesystems and NVMe, and the crypto options that iwd needs. common/hardware.config (163 options) is a hardware baseline for any platform: touchpad buses, Intel Ethernet, Wi-Fi and Bluetooth, audio, SD reader, thermal. Almost all of it is =m, so the image barely grows. Without it, the generated kernels would have no drivers for hardware that my Victus does not have.

The silent failure, and verify-fragments.sh

merge_config.sh -m plus olddefconfig silently drops any option whose dependencies cannot be satisfied: a disabled gate vendor, a missing select, a symbol that does not exist. Nothing is printed. You only find out when a driver is missing on real hardware, which for hardware I do not own means never. So verify-fragments.sh merges the fragments the same way the builder does, in a temporary directory, and compares what each fragment requested with what actually landed.

StatusMeaningResult
DEAD=y or =m was requested, and the result is n or the option does not existerror, exit code 1
DOWNGRADED=y was requested, =m came outwarning
RESURRECTEDis not set was requested, and y or m came outinfo: another option's select pulled it in
./verify-fragments.sh /usr/src/linux --target pop-001-intel-raptorlake-intel-laptop

Some "dead" results are correct by design, and the script skips them. Laptop vendor EC options on the desktop and server platforms are unreachable, because those platforms have no ACPI_BATTERY, and so are AMD_PMC and AMD_PMF on those platforms. They are counted separately as skipped by design. The script ends with a summary line of requested options and the four counters, and exits non-zero on any DEAD. I run it after every edit of a fragment.

Kconfig pitfalls I hit

  • A bool set to =m becomes n without a word. BRCMFMAC_PCIE and PINCTRL_AMD were my examples. The verifier shows them as DEAD.
  • Gate menus must be enabled explicitly. Options under X86_PLATFORM_DRIVERS_DELL and _HP, CRYPTO_HW, WWAN, WLAN_VENDOR_* and NET_VENDOR_* do nothing unless the gate is on. I added the vendor gates to the ec/* fragments and WWAN to the modem fragments.
  • Names are not what you guess. It is BT, not BLUETOOTH. USB Ethernet is USB_NET_CDCETHER. The Intel touch host controller is INTEL_QUICKI2C. Platform profiles are ACPI_PLATFORM_PROFILE.
  • Symbol case matters in scripts/config. Many "dead" options that make olddefconfig reverts turned out to be a case mistake.
  • The generic kernel must carry AMD support too. The AMD pin controller, PSP, IOMMU and PMF bits live in cpu/amd-* and also in cpu/generic-x86-64-*, because a generic image runs on AMD machines as well.
  • An Optimus laptop's panel is wired to the integrated GPU. So gpu/nvidia and gpu/nouveau also carry the iGPU drivers. The iGPU drives the internal display.
  • The seed's options may not exist in another tree. My seed comes from the CachyOS tree, which has options such as BORE that vanilla Linux does not. On a vanilla tree olddefconfig drops them silently, so a vanilla build is not bit-for-bit the same kernel.
  • One option from a real bug: the touchpad of my Victus sits on an Intel Serial IO I2C bus and does not work without MFD_INTEL_LPSS_PCI. I added it to the matrix, and on my own 7.1.8 kernel it is still disabled.

Build notes that came out of it

  • The build makes a reflinked copy of the tree for each combination. In-tree builds refuse make O=... ("source tree is not clean") and make mrproper would destroy the working kernel.
  • It builds bzImage only, with no modules. Linking thousands of =m files one by one is not cached by sccache and takes longer than the compiling.
  • mold does not work: the kernel's scripts/ld-version.sh only recognises GNU ld and LLD. The script takes ld.lld and falls back to ld.bfd.
  • GCC 15.2.1 from my overlay does not emit ENDBR64 for a few library functions called through function pointers, and objtool with CONFIG_X86_KERNEL_IBT=y treats that as a fatal error. I reproduced it deterministically on one target. GCC failed every time and clang 22 built clean, so the builder falls back to clang.
  • Building several targets through one GNU Make jobserver at -j24 beat running them as separate processes: one target alone took about 54 s, two separate processes about 80 s, and through the jobserver 46 s per target for two, 38 s for four and 14 s for six.

What was built, and what was not

A batch build on 13 and 14 August 2026 produced 304 bzImage files of about 9.3 MB each, all with release string 7.1.6-cachyos-trim11-tuned, with 0 failures and 2 warnings in the log. The nvidia targets also get a small devel archive (38 of them), because Gentoo's nvidia-drivers will not build without one. While fixing the fragments on 19 September, verify-fragments.sh reported DEAD=0 on all 304 popular targets. That is a config-resolution check only.

Ten of the kernels (generic v2 and v3, and Raptor Lake, by GPU vendor and laptop or desktop) are published for the Simple Linux installer, which also has an optional mode that builds the kernel on the new system. I verified that mode once, in a VM, for one desktop target: it built and the system booted.

What I would do differently, and open questions

  • The 304 builds predate the 19 September fixes (new common/hardware.config, fixed seed, vendor gates, WWAN, AMD bits, iGPU drivers). Only the generic kernels for the installer were rebuilt, so the full set was not.
  • I have not rerun verify-fragments.sh in the repository since the fixes, and I have not compiled the new options.
  • I cannot boot anything except the Victus. A check that a driver is present in the config is not a check that the hardware works.
  • The popularity weights are my guesses. I would replace them with real data.
  • I should have fixed the seed and written the verifier from the start, instead of discovering the leaked build state and the dropped options later.
